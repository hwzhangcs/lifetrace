# 答辩演示脚本

建议演示 8–10 分钟。打开 `http://127.0.0.1:8010`，先使用 README 中的显式 reset 命令准备 interactive 场景。

## 1. 定义问题（约 1 分钟）

“同一台无人机的编号始终是 D001，但电池和电机会被更换。我们把设备身份和部件身份分开，并用有时间范围的安装关系连接它们。”

展示总览和 D001 详情：电池 B102、相机 C004、左右电机 M031/M033。指出槽位不是自由文本备注，而是设备的结构位置。

## 2. 原子更换（约 1 分钟）

在 D001 的 battery-main 点击“更换 / 拆卸”。新部件选择 B221，操作人员选择张晓，填写原因，核对后提交。

“这个动作同时关闭 B102 的旧安装、创建 B221 的新安装、记录维修事件。三者处于同一事务。当前组成来自安装历史，不另外存一份 current_battery。”

打开 B102 时间轴，证明旧记录仍然存在。

## 3. 部件复用（约 1 分钟）

维修工作台选择 D009、battery-main，新部件选择 B102，执行安装。部件溯源中能看到 B102 曾经安装在 D001，后来安装在 D009。

## 4. 召回影响（约 2 分钟）

召回中心选择 BAT-2026-03，填写“供应商通知：潜在热失控风险”，选择操作人员并确认。

- 当前使用：D009、D014。
- 历史暴露：D001、D009、D014。
- 展开设备能看到具体部件、槽位与安装区间。

“召回不会让已安装部件自动消失。它禁止新安装，并通过真实关系查询需要处置的设备。”

## 5. 历史配置（约 1 分钟）

若刚完成交互操作，复制维修时间前后的时刻进行查询。若要固定演示 5 月与 9 月，切换到 history 种子场景，再查询 D001：

- `2026-05-01 12:00`：B102。
- `2026-09-01 12:00`：B221。
- 边界 `2026-07-10 12:00`：B221，因为有效区间左闭右开。

## 6. 回滚和并发证据（约 2 分钟）

```bash
cd backend
uv run pytest -q -k failure_after_close
uv run pytest -q tests/test_concurrency.py
```

“回滚测试在旧安装已经关闭之后，设置测试专用数据库触发器使新 INSERT 真正失败，然后比较安装表和事件表的完整快照。二者都必须恢复到操作前。”

“并发测试使用独立连接与同步屏障，两个请求同时竞争 B300，断言只能一个 201、另一个 409。召回竞争还分别控制了两个提交顺序，并观察数据库锁等待。”

不要把候选列表禁用或写入前校验称作事务回滚证明。它们是输入/业务校验，真实回滚由故障注入测试证明。

## 7. 常见答辩问题

**为什么用 PostgreSQL？** 支持关系约束与事务，并能通过范围类型和 GiST 排斥约束禁止完整历史的区间重叠。

**为什么不存 installed=true？** 是否安装可以由 removed_at 是否为空推导，重复存储会产生相互矛盾的状态。

**同一时间换电池算哪块？** 区间左闭右开，旧区间在更换时刻结束，新区间在同一时刻开始，因此只有新电池有效。

**维修人员同时提交怎么办？** 锁住资产、槽位、批次和部件，提交前重新校验；数据库约束最后兜底，旧安装 id 防止过期操作。

**为什么不给历史修改接口？** 第一版按真实时间顺序写入。历史改写需要额外的审计与校正模型，不在 MVP 范围。

**有登录吗？** 没有。用户表用于审计标签，没有进行身份认证，因此只做本地实验。

**重启恢复等于断电安全吗？** 本项目实际验证进程与容器正常重启后的持久性，不覆盖真实断电、设备损坏或灾难恢复。

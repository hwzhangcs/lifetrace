## 3. 回滚与并发的验证方法

### 回滚

保存安装表和事件表完整快照。在旧安装 `removed_at` 已写入后，创建事务内测试触发器，使下一次 installation INSERT 抛出真实数据库异常。异常离开事务后，重新读取两表，要求与快照完全相同。

这验证旧安装关闭和新增维修事件都被撤销；不会把“写入前发现部件不可用”当成回滚证明。故障注入参数只存在于内部服务调用，没有对应 HTTP 字段或测试 API。

### 并发

- 两资产竞争 B300：同步屏障同时释放请求，独立连接，恰好一个 201 和一个 409，最终 active 安装数为 1。
- 两部件竞争同一空槽：恰好一个成功。
- 两次更换竞争同一旧安装：恰好一个成功，另一个过期冲突。
- 安装与召回自然竞争：两种合法顺序均保持一致。
- 召回先持锁：通过 `pg_stat_activity` 观察安装真实等待，再提交召回，安装返回 409。
- 更换先持锁：旧安装关闭后暂停，通过数据库观察召回等待，更换提交后召回成功，影响查询包含新安装资产。

## 5. 持久性

`scripts/persistence.py` 在独立库中初始化数据，通过真实 HTTP 执行更换并保存组成、部件履历、统计快照。随后终止后端进程、重启本项目 PostgreSQL 容器、重新启动后端，再比较全部响应。

结果完全一致。该检查验证正常重启后的持久性，没有模拟真实断电、磁盘损坏和恢复协议中任意故障点。

## 6. 性能实测

数据规模：1,000 资产、10,000 部件、100,000 条安装历史，最后一组区间为当前安装。隔离库运行 ANALYZE 后逐条执行 `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)`。

| 查询 | 数据库实际执行时间 |
|---|---:|
| 单资产当前组成 | 0.039 ms |
| 单资产历史组成 | 0.060 ms |
| 批次当前影响 | 0.131 ms |
| 批次历史影响 | 7.656 ms |
| 资产分页 | 0.042 ms |

这些是本机特定样本的一次测量，包含缓存影响，不是 HTTP P95、压力测试或吞吐量承诺。完整 SQL、计划、缓冲命中和执行环境见 `performance.json`。前端维修候选列表会分页加载全部部件；若规模显著增加，应改为服务端候选搜索。
